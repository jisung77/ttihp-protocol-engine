# 두 컨텍스트가 한 파이프라인에서 UART와 SPI를 실행하는 시간표

[실행 확인] 단일 엔진은 14일차의 세 조건을 충족했다. SRAM 포함 precheck 10/10, 독립 UART TX 256/256바이트, 배선 후 점유율 100 × 68,553.7504 / 1,208,172.6720 = 5.6742%다. 이 문서는 다음 단계인 두 컨텍스트의 **소프트웨어 타이밍 실험**이다. [단일 엔진 물리 검증](https://github.com/jisung77/ttihp-protocol-engine/releases/tag/mvp-physical-38fffad)

## 한 클록에 하는 일

[추론] 짝수·홀수 클록에 A와 B의 인출 기회를 고정 배정한다. 한 컨텍스트가 명령을 인출할 때 다른 컨텍스트는 이전에 인출한 명령 하나를 실행할 수 있다. 비어 있는 슬롯은 그대로 둔다. 아래는 양쪽 FIFO에 데이터가 있고 처음 두 명령이 단순할 때의 예다.

| 클록 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| 공용 프로그램 메모리에서 읽기 | A의 첫 명령 | B의 첫 명령 | A의 다음 명령 | B의 다음 명령 |
| 공용 실행부 | 대기 | A의 첫 명령 | B의 첫 명령 | A의 다음 명령 |

[추론] 실험에서 256워드 메모리의 주소 0과 128에 각각 프로그램을 배치했다. 분기 목적지는 프로그램 시작점 기준이다. UART TX는 핀 4, SPI의 SCK·MOSI·MISO·CS는 핀 0·1·2·3을 쓴다. UART 프로그램의 핀 번호와 마스크를 바꿔 충돌을 피했다. 각 컨텍스트의 데이터는 별도로 준비하고 FIFO가 비면 해당 컨텍스트만 대기한다.

## 핀에서 확인한 결과

[실행 확인] 기존 어셈블러로 UART TX(18워드) 및 SPI 모드 0~3(조정 후 26 또는 27워드)을 바이너리로 만들었다. 4개 모드 × 인출 홀짝 배치 2가지 × 양쪽 데이터 도착 순서 2가지 = 16가지로 각각 10,000클록을 실행했다. 외부 핀 판정기는 출력·방향·MISO만 읽고 UART와 SPI를 해석했다.

| 관측값 | 16가지 결과 |
|---|---|
| UART TX 8N1 | 각 경우 0x55, 0xA6 복원. 0x55의 연속 비트 간격 434클록. 50 MHz 가정에서 50,000,000 / 434 ≈ 115,207 baud. |
| SPI 전이 | 원래 프로그램은 26+26=52클록으로 약 961.5 kHz. 지연값을 15에서 14로 바꾸고 한쪽 반주기와 CS 경계에 핀을 바꾸지 않는 명령을 배치했다. 조정 후 반주기 24·26클록, 한 주기 50클록으로 정확히 1 MHz다(50 MHz 가정). |
| SPI 전송 | 매 경우 MOSI 0x96·0x53, MISO 0x3D·0xC6 복원. 실행부의 수신 결과도 0x3D·0xC6였다. CS setup은 26클록, hold는 모드 0·2에서 26, 1·3에서 28클록이었다. |
| 동시 동작 | 매 경우 두 SPI 바이트 각각의 CS 활성 구간 안에서 UART 핀이 전이했다. UART 데이터 비트와 CS 활성이 겹친 시간은 경우별 총 257~715클록이었다. |

[추론] SPI 핀을 바꿀 수 있는 슬롯은 2클록 간격이어서 25·25를 만드는 데 제약이 있다. 24·26은 각 반주기의 25±1 조건과 평균 1 MHz를 함께 만족한다. 두 컨텍스트의 면적, WNS, 최대 동작 주파수는 RTL·배선 후에 평가한다.

[실행 확인] 별도 데이터 검사는 모드 4개 × 인출 홀짝 2가지 × 두 바이트 시험 128회 = 1,024개다. 여덟 모드·홀짝 조합 각각에서 UART, MOSI, MISO의 바이트 값 0~255를 모두 복원했다. 같은 UART 데이터와 홀짝 배치에서 상대 SPI 모드를 바꿔도 모든 클록의 UART 출력·OE 기록이 같았다. UART 전이마다 시작 에지 기준 `|t − 시작 − k × 50,000,000 / 115,200| ≤ 0.01 × 50,000,000 / 115,200`도 검사했다. 최대 오차는 0.25클록이었다. MOSI의 최소 안정 시간은 샘플 전 20클록·후 27클록이었다. 별도 자극으로 MISO가 샘플 전후 정확히 3클록 동안만 안정되게 해도 16가지 모두 같은 수신 바이트를 얻었다.

## SRAM 연속 인출

[실행 확인] IHP 256×16 SRAM 기능 모델의 단일 포트를 별도로 구동했다. 256개 주소를 서로 다른 값으로 채우고 낮은·높은 영역의 인출을 매 클록 교대로 발행했다. 시작 순서를 뒤집고 중간에 빈 슬롯도 넣었다. 다음 에지 직전의 데이터와 요청 시점에 보관한 컨텍스트 태그가 512회 모두 일치했다. 태그만 현재 요청의 것으로 바꾸면 직전 주소 0x00의 워드 0xFF00이 상대 컨텍스트로 잘못 전달돼 첫 비교에서 실패했다. 탐색 단계의 A_DLY=0 시험은 매크로가 오류를 보고해 폐기했다. 판정에는 A_DLY=1로 고정하고 매크로의 중단 요청을 실패로 처리한 실행만 사용했다. 이 시험의 RTL은 매크로를 구동하는 테스트벤치다. [테스트벤치](../experiments/two_context/sram_slots_tb.v)

## WAIT의 관측과 은퇴

[실행 확인] WAIT 시작 S=8, T=1, 동기화된 상승 사건이 9에서 처음 보이는 경우, §4에서는 9에서 성공한다. 8과 10만 확인하면 사건을 놓친다. 두 후보의 차이를 드러내는 입력을 8개 찾았다. 추가로 매 클록 사건·기한을 판정하고 자기 슬롯에서만 결과를 은퇴시키는 후보를 1,264가지 입력·취소 조합에서 독립 기준과 비교했다. 두 WAIT가 모두 9에서 성공을 판정해도 한쪽은 9, 다른 쪽은 10에서 은퇴시킬 수 있었다. 이 규칙은 v0.2 제안이며 v0.1의 S·R 계약은 그대로 유효하다. [남은 명세 결정](spec_questions.md#two-context) · [§4](../spec/spec.md#s4)

## 재현

저장소 루트에서 Python 3.11 이상으로 실행한다. Python 명령의 두 번째 인자는 결과 디렉터리다. SRAM 시험에는 Icarus Verilog와 셸이 필요하다.

```sh
python experiments/two_context/run.py . timing-run
sh experiments/two_context/check_sram.sh sram-timing
```

[실행 확인] 실행은 어셈블리·바이너리를 `images/`, 클록별 핀 기록을 `traces/`, 독립 판정과 원래 SPI 프로그램의 첫 실패를 `timing.json`에 저장한다. 압축을 푼 핀 기록은 클록마다 출력 버스, 출력 방향, 외부 MISO 순서의 3바이트다. 공식 test 워크플로에서 같은 명령의 결과를 `two-context-timing`으로 보관한다. [실험 실행기](../experiments/two_context/run.py) · [독립 핀 판정기](../experiments/two_context/check_pins.py)

[미실행] 두 컨텍스트 엔진 RTL과 매크로를 연결한 검증, 실리콘 SRAM 읽기 타이밍, 로더를 통한 컨텍스트별 적재, RX FIFO 포화, 동시 UART RX, 두 컨텍스트 하드닝·GLS 및 실물 보드 측정. 모델은 준비된 두 이미지를 곧바로 메모리에 넣고 시험할 바이트를 각 큐에 공급한다.

## 사람이 직접 확인할 지점

- `timing.json`에서 조정 전 SPI의 52클록과 조정 후 24·26클록, 두 CS 구간 안의 UART 전이를 비교한다.
- WAIT의 마지막 허용 클록에서 사건을 기억한 시점과 해당 컨텍스트의 PC가 바뀌는 시점을 구분한다.
