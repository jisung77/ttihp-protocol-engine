# 단일 통신 엔진 검증 보고서

[실행 확인] 검증 대상은 `tt_um_jisung_protocol_engine` 및 v0.1 명세다. 같은 엔진에 어셈블한 프로그램을 호스트 REQ/ACK로 적재해 UART·SPI 기능을 바꿨다. RTL은 명세를 보고 작성하고, 별도 VERIFY 작업자가 독립 ISS와 기대 벡터를 작성했다. Claude Code는 일반 시험 계획과 경계 검토를 분담했고, Codex는 원본 명세로 수용 기준을 검토하고 로컬 도구에서 실행했다. [명세](../spec/spec.md) · [검증 계획](verification_plan.md) · [결과 XML·파형·증명 해시](verification_results.json)

[실행 확인] 회로 커밋 `38fffad`의 공식 SRAM 포함 precheck는 10/10, 독립 UART TX는 256/256바이트, 배선 후 점유율은 5.6742%로 세 수용 조건을 충족했다. [물리 검증 보고서와 원본](https://github.com/jisung77/ttihp-protocol-engine/releases/tag/mvp-physical-38fffad)

### 보드용 드라이버 후속 검증

[실행 확인] 같은 하드웨어에 RP2350용 `Loader`를 연결한 기본 RTL 회귀에서 18개가 통과했다. 새 4개는 100 kHz·1 MHz 각각에서 일반 적재와 중단 프레임 복구를 검사한다. 두 시나리오에서 수락된 REQ/ACK는 각각 82회와 139회였고, §7의 K+6에서 핀 0이 구동되고 K+8에서 풀렸다. WRITE 바이트 순서를 뒤집은 드라이버 사본은 네 경우 모두 END에서 거절됐다. FIFO 재시도를 성공으로 바꾼 사본은 두 속도 모두 다섯 번째 송신에서 검출됐다. 이 두 드라이버 대조 실험은 앞의 15개 RTL 변이 집계와 별개다. [시험과 실행법](../test/README.md)

[미실행] 이 시험에서 보드의 GPIO와 MicroPython 시계는 시뮬레이터가 제공했다. 실물 보드 적재, GPIO 전기 타이밍과 ACK 100 ms 타임아웃은 이번 판정 범위 밖이다.

## 사람이 직접 확인할 지점

- `results.xml`에서 이름별 실행 여부·실패를 보고 FST에서 RUN을 수락한 에지부터 핀 데이터와 OE를 함께 본다.
- SPI 모드 1과 3은 후행 에지에서 샘플하고, RX FIFO에는 타깃이 보낸 바이트가 들어가는지 확인한다.
- 최종 GDS의 precheck와 배선 후 면적·WNS는 해당 Actions 실행의 커밋과 GDS 해시가 일치하는지 확인한다.
